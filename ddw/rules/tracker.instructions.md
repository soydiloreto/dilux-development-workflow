# Ticket Tracker Conventions

> **Tool-agnostic.** "Tracker" means whatever ticket system the team uses: Jira, Linear, Azure
> Boards, GitHub Issues, Shortcut, Trello — or none at all. DDW assumes none and requires no
> integration: with no tracker, it generates internal IDs and the pipeline works exactly the same,
> in full.

---

## Integration with the Pipeline

The tracker is consulted in the **CLASSIFY** phase and updated in the **RELEASE** phase.

When there is a tracker ticket, its ID is used as the primary `ticket` in `.ddw-state.json` (no
internal ID is generated). Every artifact, path, status line and branch uses that ID directly. The
`tracker` field in the state mirrors the same value, to signal that the ticket **comes from an
external tracker** and was not generated by DDW.

If there is no tracker, `tracker` = `null` and `ticket` is a sequential internal ID (`FEAT-001`,
`FIX-002`, `DISC-004`). **This is the default path** — nothing is degraded by not using a
tracker.

---

## Ticket Lookup (CLASSIFY phase)

### Protocol

1. Ask the user: "Is there an associated ticket in your tracker (Jira, Linear, GitHub Issues…)? If
   so, which one?"
2. If the user provides a ticket:
   - `ticket` = the tracker ID (e.g. `"PROJ-123"`, `"ENG-456"`, `"#789"`)
   - `title` = the ticket's title
   - `tracker` = the same value as `ticket`
3. If there is no ticket → ask: "Do you want me to propose one so you can file it later?"
   - If yes → propose one following this convention's format. If it gets created, apply rule 2.
   - If no → generate an internal ID (`FEAT-NNN`, `FIX-NNN`, `DISC-NNN`). `tracker` =
     `null`.

**Do not insist.** If the user does not use a tracker or does not want to, carry on with internal IDs
and do not ask again for the rest of the flow.

## Format for Proposed Tickets

*(Adapt types, priorities and workflows to the team tracker's nomenclature. The names below are the
most widespread ones; if your tool calls them something else, translate.)*

### Title
Format: `[Area] Short description in the imperative`

Examples:
- `[Auth] Implement JWT login`
- `[Payments] Fix VAT calculation in billing`
- `[API] /users endpoint returns 500 in production`

### Ticket Type

| Tier | Suggested type |
|------|----------------|
| FEATURE | Story / Task / Feature |
| FIX | Bug |

### Priority

| Severity | Suggested priority |
|----------|--------------------|
| FIX | Medium / Low / P3 |
| FEATURE | Medium / P2 |

### Description

```markdown
## Context
[Description of the problem or requirement]

## Acceptance Criteria
- [ ] [criterion 1]
- [ ] [criterion 2]

## Technical Notes
[Information relevant to whoever implements it]
```

## Ticket Update (RELEASE phase)

### Suggested Transitions

| Tier | Transition |
|------|-----------|
| FEATURE | → "Done" or "In Review" (if the PR is pending review) |
| FIX | → "Done" or "Resolved" |

### Closing Comment

Propose a comment with:

```
Resolved in commit [hash] / PR [url].

Artifacts:
- Spec/Fix-plan: [spec_path]
- PRD: [prd_path or "N/A"]

Summary: [brief description of what was implemented]

E2E evidence:
- [What was tested end to end, and the result]
- [Screenshots or logs if applicable]

Tests: [X passed, Y total]. Coverage: [XX% lines, XX% branches].

[AI-assisted]
```

**E2E evidence is mandatory in the closing comment.** "Tests pass" is not enough — you need
functional proof that the change works end to end.

### Protocol

1. Propose the transition and the comment to the user.
2. **Wait for explicit approval** before taking any action.
3. **If there is no direct tracker integration → show the text so the user can paste it manually.**
   This is the default mode: DDW installs no clients and asks for no tool's credentials.

---

## Notes for the Agent

- NEVER modify a tracker ticket without the user's approval.
- If the user has no tracker or does not want to use one, respect the decision and do not push.
- Include `Ticket: [id]` in commits and PRs when there is a tracker ticket.
- If the work reveals the ticket's scope needs updating → tell the user.
- **Do not assume a specific tool.** If the user mentions theirs, adapt the terminology to it; if
  not, use this document's generic terms.
